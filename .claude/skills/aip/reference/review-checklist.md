# review 自检清单（写活文档前逐条过）

目标永远是**文档质量**而非内容丰富度：清晰、准确、必要、最小化。**默认动作是删除或合并，不是新增**——每条新增都先过必要性关，过不了就别写。宁可少写，不要多写、错写、冗余。

1. 先查有没有同类：条目按文件名和 `aip_item.py list` 找，相近的打开全文读；主题文件按目录挑相关的读，`conventions.md` 读全文。确认不与现有内容重复/冲突；相似就合并或在 `related` 里加关联，不新增。
2. 只写自己验证过的事实（跑过命令、读过代码、复现过）；拿不准的标 draft 或投 inbox。整份清单都过了才可标 active，且在知会里给依据。
3. 必要性：半年后一个新 AI 读到它，没有这条会明显增加理解成本吗？不会就删；会但表述不清就重写；重写还不清就不写。
4. 最小化：一条只说一件事；不复述 git 历史/代码本身能推出来的信息。
5. 位置正确：坑与根因→knowledge/；可复用实现→reuse/；概念、术语、某个模块的做法→reference/ 下对应的主题文件；跨模块的铁律和不变量→conventions；旁路问题→inbox/；架构方向→decisions/。放错位置比不写危害更大。
6. 写得下：往整篇文档里加之前看一眼上限（SKILL.md「会越写越大的内容拆开写」）；要往表尾追加一行的，多半该是一条一个文件。
7. 改完跑 `aip_check`，红了当场修。

## 捕获纪律（写之前定清楚）

- **状态怎么定**：知识条目 `draft` = 证据不足、自己拿不准；`active` = 已按上面七条核过；`fixed` = 缺陷已修、教训仍有用；`superseded` = 被取代（文件头 `superseded_by` 写取代它的条目标识，被某个机制取代就写一句话）。AI 可以直接写 active，但要在知会里给依据。文件名和文件头状态一致、必填字段、`last_reviewed` 是日期、引用的条目存在、标识不重复，`aip_check` 都会查。
- **代码位置要写出来**：知识条目里把相关代码的文件路径和类名、函数名用反引号写出来（如 `src/foo.py`、`FooService.Load`）。反查靠它们在你改到这些文件时把条目列出来，到期提醒靠它们判断引用的名字还在不在；没写的只能按时间提醒。
- **推翻决策/规约**：新建一条决策，正文写「取代 <旧条目标识> + 理由」，旧条目 `aip_item.py status <旧> superseded --by <新>`；不原地改写、不删除。只改旧决策其中一条的范围时，新决策里写明改的是哪一条，旧的保持 accepted。
- **删除/合并**：只认两个理由——已被证明错误，或与另一条重复。知会里写明删了什么、依据是什么。
- **旁路问题**：看过了决定不做的改 `wontfix`（别留着占 open）；真做完了改 `closed`。

## 整份 `.aip/` 的 review

触发条件在 SKILL.md。做法：

1. 对每个活文档过上面七条，发现的问题用「问题点 + 修改建议 + 理由 + 影响」格式列出来再改。
2. 对照现状核事实：`aip_upkeep.py --all` 列出的 knowledge 逐条重验（仍成立就 `aip_item.py reviewed`，缺陷已修改 `fixed`，被取代改 `superseded`）；主题文件和可复用实现里的构件、路径是否还在；主题文件的 `read_when` 还准不准；inbox/ 里已闭环的改 `closed`；tracks/ 里做完的删掉（`aip_item.py status <线> done`）。
3. 顺带核项目技能和说明文件（`CLAUDE.md` / `AGENTS.md`、项目技能目录）里的路径、命令、叫法是否还和现状一致。
4. 做完把 `config.yaml` 的 `review_last_full` 改成当天，随本次提交。

review 只管文档质量，不做问题分析。
